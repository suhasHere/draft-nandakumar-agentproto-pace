PACE: Protocol for Agent Communication Exchange

Abstract

This document defines the Protocol for Agent Communication Exchange (PACE), a session protocol for communication between AI agents and between agents and tools over Media over QUIC Transport (MOQT). PACE provides session lifecycle management, multi-modal data exchange (real-time media, chat, tool calls, file transfers), agent identity verification, and delegated authorization — all within a unified publish/subscribe transport that supports point-to-point and point-to-multipoint topologies.¶

The protocol maps agent communication patterns onto MOQT primitives, leveraging MOQT's relay infrastructure for scalable fan-out, priority-based delivery, and graceful recovery from network failures through relay caching and QUIC connection migration.¶

1. Introduction

AI agents are autonomous, adaptive intelligent software systems that use AI models to complete specific tasks. These agents interact via chat or voice, making decisions, executing actions, and communicating with other agents and tools independently. As agent-to-agent and agent-to-tool communication expands across the Internet, reliable interoperability across platforms and vendors becomes critical.¶

The AI agent ecosystem presents unique communication requirements that existing transport protocols do not fully address:¶

Agent Identity:

Agents may need to be authenticated independently of the users they represent. Verifiable agent identity enables independent revocation, scoped permissions, and auditability of agent-initiated actions.¶

Capabilities and Collaboration:

Agents have specialized capabilities enhanced through collaboration. This raises considerations for selecting agents and tools, initiating communication, and maintaining interactions across network boundaries.¶

Interaction Characteristics:

Agent interactions can be long-lived, utilize significant amounts of context across various modes (text, audio, video), and require very low latency. This introduces considerations around reliability, transport session management, and efficient data transport.¶

Security and Privacy:

Protecting data over untrusted networks requires mechanisms for identity verification, confidentiality, integrity, authenticity, and delegated authorization across AI agent chains.¶

This document defines the Protocol for Agent Communication Exchange (PACE), which addresses these requirements by providing a session layer over Media over QUIC Transport (MOQT) [MoQ-TRANSPORT]. PACE enables diverse agent protocols to leverage MOQT's real-time streaming capabilities, built-in prioritization, scalable relay infrastructure, and efficient multiplexing over QUIC.¶

1.1. Design Goals

PACE is designed to meet the following objectives:¶

  1. Session Lifecycle Management: Provide timed session management (short or long-lived) covering establishment, update, context handling, and termination.¶

  2. Multi-Modal Data Exchange: Support concurrent exchange of real-time data (voice/video), semi-real-time data (chat/streaming text), and non-real-time data (tool calls/file transfers).¶

  3. Scalable and Reliable: Enable highly scalable session management that survives network and server failures with graceful recovery.¶

  4. Flexible Topologies: Support point-to-point and point-to-multipoint communication patterns through relay infrastructure.¶

  5. Agent Identity and Authorization: Provide mechanisms for agent authentication independent of user identity, with delegated authorization and fine-grained behavioral scopes.¶

  6. Protocol Agnostic: Serve as a session substrate usable by application-layer protocols (A2A, MCP, and others) with appropriate layering and extension points.¶

1.2. Requirements Language

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

2. Architecture Overview

Figure 1 illustrates the overall PACE architecture, showing how the session protocol layers over MOQT and QUIC, and how application protocols integrate through the extension framework.¶

2.1. MOQT as Session Substrate

Media over QUIC Transport (MOQT) [MoQ-TRANSPORT] is a publish/subscribe protocol built on QUIC that delivers low-latency, highly-scalable message distribution. MOQT decouples publishers from subscribers through intermediary relay infrastructure, enabling efficient fan-out to many consumers without requiring direct connections between endpoints.¶

MOQT provides several properties essential for agent communication:¶

  • Named Data Addressing: Content is addressed by hierarchical namespace tuples rather than endpoint locations, enabling location-independent data retrieval and natural caching¶

  • Application Layer Multicast: Relay infrastructure provides multicast-like fan-out without requiring network-layer multicast, making one-to-many distribution practical across the public Internet¶

  • Low Latency: QUIC's 0-RTT connection establishment, stream multiplexing to prevent head-of-line blocking, and priority-based delivery (0-255 scale) ensure time-critical messages are transmitted first¶

  • High Scalability: Publishers connect once to a relay which fans out to all subscribers; hierarchical relay networks distribute load across geographic regions¶

  • Fault Tolerance: Relay redundancy enables failover without disrupting active sessions; object caching at relays enables recovery from transient disconnections¶

Figure 2 illustrates the relay architecture that enables PACE's scalability and reliability properties.¶

3. Session Management

An PACE session represents a logical communication context between two or more agents. Sessions are the fundamental unit of interaction, providing lifetime management, context preservation, and failure recovery.¶

3.1. Session Lifecycle

Sessions progress through defined states:¶

IDLE:

No session exists. Agent is available to initiate or accept sessions.¶

PENDING:

Session establishment in progress. Capability negotiation and authentication are being performed.¶

ACTIVE:

Session is established and data exchange is occurring. Sessions can be updated (renegotiate capabilities, add participants) while active.¶

SUSPENDED:

Session is temporarily inactive but state is preserved. The session may be resumed without full re-establishment. Sessions automatically transition to CLOSED after a configurable timeout.¶

CLOSED:

Session has terminated. Resources are released and state is cleaned up.¶

3.2. Session Establishment

Session establishment combines MOQT connection setup with PACE-specific negotiation of session parameters, agent identity, and capabilities.¶

During session establishment, agents exchange the following information:¶

3.2.1. Session Parameters

  • session-id: Globally unique session identifier (UUID)¶

  • session-type: Short-lived (bounded duration) or long-lived (indefinite)¶

  • session-timeout: Maximum idle duration before automatic termination¶

  • max-participants: Maximum number of agents in the session¶

  • supported-modalities: Bitmask of data modalities the agent can handle¶

3.2.2. MOQT Setup Extensions

PACE defines the following MOQT setup parameters negotiated during CLIENT_SETUP/SERVER_SETUP:¶

Table 1
Parameter ID Description
pace-version 0x50414301 PACE protocol version
agent-identity 0x50414302 Agent identity token or certificate reference
supported-protocols 0x50414303 Bitmask of application protocols (A2A=0x01, MCP=0x02)
auth-schemes 0x50414304 Supported authentication schemes
session-capabilities 0x50414305 Session capability flags

3.3. Timed Sessions

PACE supports both short-lived and long-lived sessions to accommodate different agent interaction patterns:¶

Short-Lived Sessions:

Bounded duration sessions for discrete operations such as a single tool invocation or query. The session has a defined maximum lifetime and automatically terminates upon completion or timeout. Optimized for low-overhead interactions.¶

Long-Lived Sessions:

Indefinite sessions for ongoing collaboration, monitoring, or persistent agent relationships. These sessions survive idle periods through the SUSPENDED state and can be resumed without full re-establishment. Suitable for complex multi-step tasks, ongoing advisory relationships, or persistent tool connections.¶

Session timing is governed by the session-timeout parameter, which defines the maximum idle period before automatic transition to CLOSED. Agents MAY send keepalive messages to prevent timeout during periods of inactivity.¶

3.4. Session Update

Active sessions can be updated to renegotiate parameters without terminating the session:¶

  • Adding or removing data modalities¶

  • Adjusting priority mappings¶

  • Adding participants (transitioning from point-to-point to multipoint)¶

  • Updating authorization scopes¶

  • Extending session timeout¶

Updates are performed by publishing a SESSION_UPDATE message on the session control track. All participants MUST acknowledge the update before new parameters take effect.¶

3.5. Session Recovery

PACE provides graceful recovery from network and server failures through multiple mechanisms:¶

QUIC Connection Migration:

QUIC's connection ID mechanism allows sessions to survive network path changes (e.g., WiFi to cellular) without re-establishing the MOQT session.¶

Relay Caching:

MOQT relays cache recent objects, allowing agents that reconnect after transient disconnections to receive missed messages from cache without requiring the peer to retransmit.¶

Session Resumption:

Agents that experience prolonged disconnections can resume SUSPENDED sessions by re-authenticating and providing the session-id. The relay provides cached context from the point of disconnection.¶

State Checkpointing:

Agents SHOULD periodically publish session state checkpoints on a dedicated state track. These checkpoints enable recovery of session context after relay failures.¶

3.6. Session Termination

Sessions are terminated explicitly via SESSION_CLOSE or implicitly via timeout. Upon termination:¶

  1. All active subscriptions are cancelled¶

  2. Pending operations receive cancellation notifications¶

  3. Session state and cached objects are retained for a configurable grace period to handle in-flight messages¶

  4. After the grace period, all session resources are released¶

4. Agent Identity and Discovery

4.1. Agent Identity Model

PACE defines an identity model where agents are authenticated independently of the users they represent. This separation enables:¶

  • Independent revocation of agent credentials without affecting user accounts¶

  • Scoped permissions specific to agent capabilities¶

  • Auditability of agent-initiated actions distinct from user actions¶

  • Delegation chains where agents act on behalf of other agents¶

4.1.1. Agent Identity Token

Each agent presents an identity token during session establishment. The token contains:¶

The token format is based on JWT [RFC7519] with agent-specific claims.¶

4.1.2. Delegation Chains

When an agent acts on behalf of another agent (e.g., a sub-agent invoked to handle a specialized task), the identity token includes a delegation chain that traces the authorization path:¶

Delegation Chain Example:

User "alice" → Agent "coordinator" → Agent "researcher" → Tool "web-search"

Each agent's token contains:
  delegation-chain: [
    { agent: "coordinator", scope: "research.execute", granted-by: "alice" },
    { agent: "researcher", scope: "web.search", granted-by: "coordinator" }
  ]
¶

Receiving agents and tools can verify the complete delegation chain to ensure each link in the chain has appropriate authorization.¶

4.2. Agent Discovery

PACE provides in-band agent discovery through MOQT's namespace operations, enabling agents to find and evaluate potential collaborators within a session context.¶

4.2.1. Discovery Protocol

Agents advertise their presence using PUBLISH_NAMESPACE and discover others using SUBSCRIBE_NAMESPACE:¶

4.2.2. Agent Capability Card

Each agent publishes a capability card as an MOQT object on its discovery track. The card advertises the agent's identity, capabilities, supported modalities, and connection parameters:¶

{
  "agent-id": "researcher-agent-01",
  "name": "Research Assistant",
  "description": "Specialized agent for web research and summarization",
  "version": "1.2.0",
  "identity": {
    "issuer": "https://identity.example.com",
    "public-key-id": "key-2026-06"
  },
  "capabilities": {
    "modalities": ["text", "structured-data", "files"],
    "streaming": true,
    "multi-party": true,
    "max-concurrent-tasks": 10
  },
  "supported-protocols": ["a2a", "mcp"],
  "authentication": {
    "schemes": ["bearer", "dpop", "mtls"],
    "token-endpoint": "https://auth.example.com/agent/token"
  },
  "transport": {
    "relay-endpoint": "moqt://relay.example.com:4443",
    "namespace-prefix": "pace/session-123/researcher-agent-01",
    "supported-extensions": ["pace-v1"]
  }
}
¶

5. Multi-Modal Data Exchange

PACE supports concurrent exchange of multiple data modalities within a single session, each with appropriate quality of service. This enables agents to simultaneously conduct text-based reasoning, stream audio/video, invoke tools, and transfer files.¶

5.1. Modality Types

PACE defines the following data modality classes:¶

Table 2
Modality Latency Examples Delivery
Real-time < 100ms Voice, video, screen share Continuous stream
Semi-real-time < 1s Chat messages, streaming LLM output Ordered objects
Non-real-time Best effort Tool calls, file transfers, context Reliable delivery

5.2. Channel Architecture

Each modality is mapped to dedicated MOQT tracks (channels) within the session namespace. Channels provide isolation between modalities while sharing the same session context and authorization.¶

5.3. Priority and Quality of Service

MOQT's 0-255 priority scale enables differentiated treatment of messages based on their urgency and modality. PACE defines the following priority tiers:¶

Table 3
Priority Range Category Use
0-15 Critical Control Session termination, emergency cancel
16-31 Urgent Control Error notifications, auth revocation
32-63 Real-time Media Voice/video frames
64-95 Interactive Chat messages, streaming LLM tokens
96-127 Standard Operations Tool calls, request/response
128-159 Discovery Capability cards, agent advertisements
160-191 Background Telemetry, non-critical notifications
192-255 Bulk Transfer File transfers, context exchange

5.3.1. Group Order

MOQT Group Order controls delivery sequencing within a track:¶

  • Real-time media: Descending order (newest first, drop stale frames)¶

  • Chat/streaming text: Ascending order (preserve message sequence)¶

  • Operations: Ascending order (preserve execution order)¶

  • Bulk transfers: Ascending order (sequential chunk delivery)¶

5.4. Request/Response Pattern

Request/response interactions use coordinated publish and subscribe operations through the MOQT relay:¶

5.5. Streaming Pattern

Long-running operations produce incremental results as a stream of MOQT objects organized into groups representing execution phases:¶

Groups serve as synchronization points. The server advances to a new group when transitioning between execution phases. Late-joining subscribers receive the latest complete group from relay cache.¶

5.6. Real-Time Media Exchange

For voice and video communication between agents (or between agents and humans), PACE maps media streams to dedicated real-time tracks with appropriate priority and delivery semantics:¶

  • Audio frames are published as individual MOQT objects with descending group order (newest-first delivery for real-time playback)¶

  • Video frames use group-based organization where each group represents a decodable unit (e.g., GOP)¶

  • MOQT's priority mechanism ensures media frames preempt lower-priority data when bandwidth is constrained¶

6. Communication Topologies

PACE supports multiple communication topologies through MOQT's relay infrastructure.¶

6.1. Point-to-Point

Direct communication between two agents through a relay:¶

Point-to-Point:

  Agent A ──────▶ Relay ──────▶ Agent B
         ◀──────        ◀──────
¶

This is the simplest topology, used for tool invocation, simple task delegation, and bilateral collaboration.¶

6.2. Point-to-Multipoint (Fan-Out)

One agent publishes to multiple subscribers through relay fan-out:¶

Point-to-Multipoint:

                         ┌──▶ Agent B (subscriber)
                         │
  Agent A ──▶ Relay ─────┼──▶ Agent C (subscriber)
  (publisher)            │
                         └──▶ Agent D (subscriber)
¶

This topology enables broadcast notifications, shared context distribution, and one-to-many task delegation where multiple agents observe the same operation.¶

6.3. Multi-Party Collaboration

Multiple agents publish and subscribe within a shared session, enabling group collaboration:¶

Multi-Party:

  Agent A ◀──┐         ┌──▶ Agent A
             │         │
  Agent B ◀──┼─ Relay ─┼──▶ Agent B
             │         │
  Agent C ◀──┘         └──▶ Agent C

  (All agents publish and subscribe to shared tracks)
¶

Multi-party sessions use MOQT namespace operations to manage participant membership. Each participant publishes to their own tracks and subscribes to relevant tracks from other participants.¶

6.3.1. Participant Management

Adding a participant to an active multi-party session:¶

  1. New agent establishes MOQT connection to the relay¶

  2. New agent publishes SESSION_JOIN on the session control track¶

  3. Existing participants receive the join notification¶

  4. Existing participants publish updated capability information¶

  5. New agent subscribes to relevant tracks from other participants¶

  6. Session state (participant list, shared context) is updated¶

6.4. Hierarchical Teams

Agents can form hierarchical structures where a coordinator delegates subtasks to specialist agents:¶

Hierarchical Team:

                     ┌──────────────┐
                     │ Coordinator  │
                     │    Agent     │
                     └──────┬───────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
       ┌──────▼─────┐ ┌────▼──────┐ ┌────▼──────┐
       │ Researcher │ │  Writer   │ │ Reviewer  │
       │   Agent    │ │  Agent    │ │   Agent   │
       └──────┬─────┘ └───────────┘ └───────────┘
              │
       ┌──────▼─────┐
       │ Web Search │
       │   Tool     │
       └────────────┘
¶

Each level in the hierarchy operates as a separate PACE session with its own authorization scope. The coordinator's delegation chain is extended at each level, maintaining an auditable path from the original user authorization.¶

7. Authorization and Security

7.1. Authorization Model

PACE implements a fine-grained, behavior-driven authorization model where access tokens are scoped to specific operations an agent is permitted to perform.¶

7.1.1. Behavior-Driven Scopes

Unlike traditional role-based access, PACE scopes are bound to specific agent behaviors:¶

Scope Structure:

  {domain}:{resource}:{action}:{constraints}

Examples:
  research:web:search:max-queries=10
  tools:filesystem:read:path=/data/*
  agents:coordinator:delegate:max-depth=2
  chat:session-123:send:modality=text
  media:session-123:publish:type=audio,video
¶

Scopes can include dynamic constraints that limit the scope based on runtime context (time bounds, resource limits, geographic restrictions).¶

7.1.2. Delegated Authorization

When agents invoke other agents or tools on behalf of a user, PACE supports delegated authorization that preserves the principle of least privilege:¶

Each delegation narrows the scope, ensuring downstream agents cannot exceed the permissions of their delegator. The complete delegation chain is verifiable by any participant.¶

7.1.3. Authorization Token Exchange

Authorization tokens are exchanged during session establishment and can be refreshed during active sessions without interruption:¶

  1. Agent presents initial authorization token in SESSION_INIT¶

  2. Receiving agent validates the token and delegation chain¶

  3. If additional scopes are needed, agents negotiate via the auth control channel¶

  4. Token refresh is performed proactively before expiration¶

7.1.4. Confirmation and Evidence

For high-risk operations, PACE supports confirmation requirements where an agent must present evidence that a human or authorized system has approved the action:¶

  • confirmation-required: Operation requires explicit approval¶

  • evidence-type: Type of evidence (human-approval, policy-check, mfa)¶

  • evidence-token: Cryptographic proof of confirmation¶

This mechanism mitigates the impact of compromised agents or hallucination-driven actions by requiring out-of-band verification for sensitive operations.¶

7.2. Transport Security

All PACE communication is encrypted via TLS 1.3 as provided by the underlying QUIC connection. Additionally:¶

  • Agent identity tokens are cryptographically signed and verifiable¶

  • Session control messages are integrity-protected¶

  • Relay nodes operate on encrypted traffic without access to payload content (unless explicitly authorized as trusted intermediaries)¶

  • MOQT's Common Access Token [MoQ-C4M] provides relay-level authorization for namespace access¶

7.3. Privacy Considerations

  • Agents SHOULD minimize the context and data shared in sessions to what is necessary for the task¶

  • Session metadata (participant identities, timing, access patterns) should be protected from unauthorized observation¶

  • Long-lived sessions SHOULD support forward secrecy through periodic key rotation¶

  • Relay operators MUST NOT retain session content beyond the operationally required caching period¶

8.2. Application Protocol Multiplexing

Multiple application protocols can coexist within a single PACE session by using protocol-specific sub-categories:¶

8.3. Relay Routing

MOQT relays route subscriptions based on namespace prefixes. The hierarchical structure enables:¶

  • Session-level routing: All traffic for a session shares a prefix¶

  • Agent-level routing: Traffic to/from specific agents is identifiable¶

  • Category-level routing: Relays can apply different policies per category (e.g., prioritize real-time, rate-limit bulk transfers)¶

9. MOQT Transport Binding Layer

This section defines the concrete MOQT transport mechanics that underpin PACE sessions. While Section 3 defines session lifecycle and Section 5 defines multi-modal channels, this section specifies the precise mapping of protocol messages to MOQT primitives, including connection establishment sequences, message serialization formats, and operation-to-primitive mappings.¶

9.1. Connection Establishment

Agents using PACE MUST establish either a native QUIC connection or a WebTransport [WebTransport] session as defined in [MoQ-TRANSPORT]. For native QUIC connections, agents MUST use the ALPN value "moqt". For WebTransport, the protocol is negotiated using the "WT-Available-Protocols" mechanism as specified in [MoQ-TRANSPORT].¶

The connection setup follows this sequence:¶

During the MOQT setup phase, agents negotiate the PACE setup parameters defined in Section 3 (pace-version, agent-identity, supported-protocols, auth-schemes, and session-capabilities) as MOQT extensions in CLIENT_SETUP and SERVER_SETUP messages.¶

9.2. Track Organization

Agent protocol messages are mapped to MOQT tracks using a hierarchical namespace structure as defined in [MoQ-TRANSPORT]. MOQT namespaces consist of 1-32 ordered tuple fields, enabling relays to route based on hierarchical prefixes.¶

9.2.1. Full Track Name Structure

The first namespace field is always "pace" identifying the protocol. Subsequent fields provide session routing, agent identification, and category-based message classification as defined in Section 8.¶

9.2.2. Track Category Mechanics

Tracks are organized into categories that map to MOQT publish/subscribe operations:¶

Table 5
Category Direction MOQT Mechanism Purpose
ctrl Bidirectional PUBLISH + SUBSCRIBE Session lifecycle
discovery Publish PUBLISH_NAMESPACE + OBJECT Agent advertisement
ops/request Client→Server PUBLISH + OBJECT Request messages
ops/response Server→Client PUBLISH + OBJECT Response messages
rt Bidirectional Continuous PUBLISH Real-time media
chat Bidirectional PUBLISH + OBJECT Chat/streaming text
data Bidirectional PUBLISH + OBJECT(s) Bulk transfers

Subscribers discover available tracks within a category using SUBSCRIBE_NAMESPACE on the category prefix, receiving NAMESPACE announcements as new tracks appear.¶

9.3. Message Serialization

Agent protocol messages are serialized and encapsulated within MOQT objects. Each MOQT object contains a header (managed by the MOQT layer) and a protocol-specific payload:¶

The PACE message envelope prepends minimal framing:¶

  • version (1 byte): PACE envelope version (currently 0x01)¶

  • flags (1 byte): Message flags (0x01=compressed, 0x02=fragmented, 0x04=encrypted)¶

  • length (varint): Length of the serialized protocol message¶

Protocol bindings SHOULD preserve native message formats where possible to maintain compatibility with existing protocol implementations. For example, A2A messages retain their JSON-RPC 2.0 format; the PACE envelope simply wraps the serialized JSON bytes.¶

10.2.5. Streaming Support

A2A streaming operations (SendStreamingMessage, task subscriptions) use MOQT groups and objects following the streaming pattern in Section 5.5.¶

A2A defines two streaming event types:¶

TaskStatusUpdateEvent:

Published when task state changes. Contains task ID, current state (queued, running, completed, failed, canceled), and optional message.¶

TaskArtifactUpdateEvent:

Published when task produces output. Contains artifact data (text, files, structured data) with incremental or complete delivery.¶

The mapping to MOQT objects:¶

  • Each streaming response creates a new MOQT group¶

  • Incremental updates are individual objects within the group¶

  • TaskStatusUpdateEvent and TaskArtifactUpdateEvent map to objects¶

  • Groups represent execution phases (initialization, progress, completion)¶

10.6. Multi-Agent Orchestration Patterns

The binding layer supports common multi-agent coordination patterns. Each pattern leverages MOQT's pub/sub and relay capabilities:¶

10.6.1. Sequential Orchestration

Agents execute tasks in sequence, each passing results to the next:¶

Sequential Pattern:

Agent A ──result──▶ Agent B ──result──▶ Agent C
  │                    │                    │
  └─ publish to ──────▶└─ subscribe + ─────▶└─ subscribe +
     B's request         publish to           publish to
     track               C's request          result track
                         track
¶

Each agent subscribes to its predecessor's response track and publishes to the next agent's request track. MOQT groups track pipeline stages.¶

10.6.2. Concurrent (Broadcast) Pattern

A coordinator distributes work to multiple agents simultaneously:¶

Concurrent Pattern:

                 ┌──▶ Agent B (specialist)
                 │       │
Coordinator ─────┼──▶ Agent C (specialist)
  (publish)      │       │
                 └──▶ Agent D (specialist)
                         │
                 ◀── all subscribe to ───┘
                     coordinator's
                     result aggregation track
¶

The coordinator publishes a single request object; MOQT relay fan-out delivers it to all subscribing specialists. Results are published back to a shared aggregation track.¶

10.6.3. Handoff Pattern

An agent transfers an active task to another agent:¶

Handoff Pattern:

Agent A ══task══▶ [publishes HANDOFF on ctrl track]
                       │
                       ▼
               Agent B subscribes to task track,
               receives cached context from relay,
               continues execution
¶

The handoff leverages MOQT's relay caching — Agent B receives the full task context (prior groups) upon subscribing, enabling seamless continuation without explicit state transfer.¶

10.6.4. Hierarchical Teams

See Section 6 for topology description. In the binding layer, hierarchical teams use nested PACE sessions where each coordinator maintains a parent session and creates child sessions for sub-task delegation. Delegation chains (Section 4) ensure authorization propagates correctly through the hierarchy.¶

MOQT delivers reliability and resilience via QUIC connection migration, relay caching for recovery from transient disconnections, session suspension/resumption, and graceful degradation under load.¶

12. Scalability and Reliability

12.1. Relay Network Architecture

PACE inherits MOQT's relay architecture for geographic distribution and load management:¶

Properties of the relay network:¶

  • Subscription Aggregation: Multiple subscribers to the same track result in a single upstream subscription, reducing origin load¶

  • Geographic Locality: Edge relays cache content close to subscribers, minimizing round-trip latency¶

  • Load Distribution: Hierarchical structure prevents hotspots and single points of failure¶

  • Fault Isolation: Relay failures are localized; other paths continue operating¶

12.2. Caching Strategy

MOQT relays implement tiered caching optimized for agent communication:¶

Table 18
Cache Tier TTL Content
Hot Seconds Active operation responses, real-time state
Warm Minutes Agent capability cards, session metadata
Cold Hours Historical context, audit logs

Caching enables:¶

  • Late-joining participants receive current session state¶

  • Recovery from transient disconnections without peer retransmission¶

  • Reduced load on agent endpoints through relay-served responses¶

  • Efficient multipoint distribution of shared context¶

12.3. Failure Modes and Recovery

Failure Detection Recovery

Relay failure Subscription timeout Failover to alternate relay

Prolonged outage Session timeout Session closed, state checkpointed

13. Security Considerations

13.1. Threat Model

PACE considers the following threats:¶

  • Unauthorized agents joining sessions or impersonating legitimate agents¶

  • Man-in-the-middle attacks on agent communications¶

  • Privilege escalation through delegation chain manipulation¶

  • Denial of service via excessive session creation or message flooding¶

  • Data exfiltration through compromised relay nodes¶

  • Hallucination-driven operations by compromised or malfunctioning agents¶

13.2. Mitigations

  • All transport is encrypted via TLS 1.3 (QUIC requirement)¶

  • Agent identity tokens are cryptographically signed with short expiry¶

  • Delegation chains are validated end-to-end at each hop¶

  • Relay authorization via MOQT Common Access Tokens restricts namespace access¶

  • Rate limiting at relay nodes prevents flooding¶

  • Confirmation requirements for high-risk operations prevent hallucination-driven damage¶

  • Session timeout and explicit termination prevent resource exhaustion¶

13.3. Relay Trust Model

MOQT relays are trusted for routing but NOT for content inspection. Relay operators:¶

  • MUST NOT inspect or modify message payloads¶

  • MUST enforce namespace-level access control¶

  • MUST implement rate limiting and abuse prevention¶

  • MAY cache objects for operational efficiency¶

  • MUST NOT retain cached content beyond operational necessity¶

For deployments requiring end-to-end confidentiality even from relay operators, agents MAY implement payload encryption above the PACE layer.¶
